可以这样理解，两者本质上都是在做 **数据整合 + 数据可追溯性（lineage / provenance）**，区别在于输入数据类型和处理方式：

- **非结构化数据**：主要做 **Integration + Provenance**。把 PDF、报告、会议记录、邮件、网页等内容解析、切分、抽取实体和关系，再整合到统一的数据模型中，同时保留每个结论来自哪个原始文档、哪一页或哪一段。
- **结构化数据**：主要做 **ELT + Lineage / Provenance**。把数据库、CSV、API、EHR 表格等数据先加载到统一平台，再进行清洗、转换、Join、字段映射和建模，同时记录每个字段从哪个 source table、经过哪些 transformation 得到。

一句话概括就是：

**非结构化数据是“把信息变成可用的数据，并追溯证据来源”；结构化数据是“把已有数据统一转换建模，并追溯数据处理链路”。**

如果放到你现在 VC diligence Agent 的语境里，就是 **文档侧做 evidence provenance，数据库侧做 ELT lineage，最后把两条链合并成一个可验证的数据层。**

对，这两个其实不应该被硬塞成同一条技术流程，因为它们解决的是两类不同问题。更合理的架构是：**两条数据处理链，最后汇合到同一个 Due Diligence Evidence Layer。**

结构化数据这边，重点是 **数据转换和计算链路溯源**。输入是 CSV、Excel、数据库、CRM、财务系统、API。流程更像：**Extract/Load → Schema mapping → Cleaning → Transformation → Metric calculation → Data lineage → Reconciliation**。这里核心问题不是“这句话来自哪一页”，而是“这个 $12M ARR 是由哪些原始字段、经过什么公式算出来的”。

所以你们可以把产品设计成：

**Unstructured Evidence Pipeline**
负责回答：**Where did this claim come from?**

**Structured Financial/Data Pipeline**
负责回答：**How was this number produced?**

然后两者汇合到：

**Unified Verification Layer**
负责回答：**Can this claim or number actually be trusted?**

例如报告里写：

**“Company ARR reached $12M in 2026.”**

系统可以同时展示两种 provenance：

**Evidence provenance：** 这个说法来自 Pitch Deck 第 18 页。
**Data lineage：** CRM monthly recurring revenue → cleaned customer table → MRR aggregation → ×12 → calculated ARR = $9.6M。

这样系统进一步发现：

**Claimed ARR = $12M**
**Calculated ARR = $9.6M**
→ **Mismatch flagged**

这其实比单纯做“数据溯源”更强。你们真正可以讲的不是一个 provenance tool，而是：

**AI Due Diligence Verification Infrastructure**

它统一解决两种可信度问题：

**Unstructured data → evidence provenance**
**Structured data → computational lineage**
**Final report → claim verification + discrepancy detection**

这样产品逻辑会清楚很多，也能自然把你刚才说的 financial number verification 包进去。

黑客松里不要真的做完整的企业级 ELT、数据治理和 Agent Marketplace。最合理的是做一个**能完整跑通“上传数据 → 验证 → 生成可追溯报告”闭环的 MVP**。

可以把技术实现压缩成 5 层：

### 1. Data Ingestion

支持两类输入：

**非结构化数据**

- PDF / Pitch Deck / Contract / Research Report
- 用 `PyMuPDF / pdfplumber` 提取文本
- 每段保存：

  - `document_id`
  - `page`
  - `chunk_id`
  - `raw_text`

**结构化数据**

- CSV / Excel
- 用 `pandas`
- 保存原始表，同时建立字段级 metadata：

  - source file
  - sheet
  - column
  - row

黑客松里不用接真实 Snowflake、Salesforce、QuickBooks，直接用几份模拟 startup data room 文件即可。

---

### 2. Evidence Extraction

LLM 从非结构化文档里抽取关键 claim，例如：

```json
{
  "claim": "2026 ARR is $12M",
  "value": 12000000,
  "source": "PitchDeck.pdf",
  "page": 18,
  "evidence": "Our ARR reached $12M..."
}
```

这里可以用 OpenAI / Claude structured output。

核心不是复杂 RAG，而是确保每个 claim 都绑定一个**source pointer**。

---

### 3. Structured Data Lineage

对于 Excel / CSV，不要让 LLM 自己算数字。

直接用 Python 做 deterministic calculation，例如：

```python
mrr = df["monthly_recurring_revenue"].sum()
arr = mrr * 12
```

同时记录：

```json
{
  "metric": "ARR",
  "value": 9600000,
  "inputs": [
    "revenue.csv.monthly_recurring_revenue"
  ],
  "transformation": "SUM(MRR) * 12"
}
```

这就是你们 hackathon 版本的 **Data Lineage**。

---

### 4. Verification Engine

这是整个项目最重要的技术模块。

让系统自动比较：

```
Claim from Pitch Deck
ARR = $12M

Calculated from raw data
ARR = $9.6M

Difference = 25%
```

然后写简单规则：

```python
if abs(claimed - calculated) / calculated > 0.05:
    status = "FLAGGED"
```

再让 LLM 解释：

> Pitch deck reports $12M ARR, while revenue records support approximately $9.6M annualized revenue.

这里形成：

**Evidence → Calculation → Conflict Detection → Explanation**

这会比单纯让 LLM “判断有没有问题”可信很多。

---

### 5. Agent + Report UI

Marketplace 不需要真的做几十个 Agent。

做 3 个 demo Agent 就够了：

**Financial Agent**
验证 Revenue、ARR、Growth、Burn、Runway。

**Market Agent**
检查市场规模、竞争对手、市场 claim 的来源。

**Company / Risk Agent**
综合其他 Agent 输出，生成 risk summary。

前端可以用 **Next.js / React**，后端用 **FastAPI + Python**。

最终 UI 最重要的是一个表格：

| Claim | Reported | Verified | Status | Evidence |
| --- | --- | --- | --- | --- |
| ARR | $12M | $9.6M | ⚠️ Conflict | View source |
| Growth | 80% | 76% | ✓ | View calculation |
| Customers | 120 | 118 | ⚠️ | View source |

点击 **View source** 后，直接跳到 PDF 页码或者展示：

**Source → Original text → Raw data → Formula → Final result**

你们这个产品里，**非结构化数据最合理的来源不是“全网乱搜”，而是围绕 VC 尽调场景分成内部 Data Room 和外部公开证据两类。**

最核心的是 **Startup Data Room**，包括 Pitch Deck、Business Plan、投资人更新、客户合同、LOI、销售材料、董事会材料、产品说明、技术白皮书、临床报告、专利文档、管理层提供的 PDF/Word/PPT，以及创始人访谈或会议记录。这些是“公司自己声称什么”的主要来源，也是你们做 claim extraction 和 provenance 的第一层。

第二类是 **External Evidence Sources**，用来验证公司自己的说法，例如公司官网、新闻报道、行业研究报告、SEC/监管文件、专利数据库、ClinicalTrials.gov、PubMed、FDA 公开文件、招聘页面、GitHub、LinkedIn 公司页等。它们的作用是做 cross-source verification，比如公司说“已进入 50 家医院”，系统可以进一步查官网、新闻稿、客户案例或公开合作信息，看这个 claim 是否有独立证据支持。

所以你们可以把非结构化数据源定义成：

**Internal company documents + External third-party evidence**

最适合黑客松 demo 的组合其实很简单：`Pitch Deck + Customer Contract + Technical Report + Market Report + Website/News evidence`。然后让系统展示一个 claim 如何从内部文件被抽取，再被外部来源验证或反驳。

如果你们想把产品逻辑说得更专业，可以直接定义为两层：

**Primary Evidence：公司直接提供的材料**
**Independent Evidence：第三方公开来源**

这样最终报告里每个结论不仅有“source”，还可以有一个很强的字段：**Evidence Independence**，也就是这个结论到底只是公司自己说的，还是有第三方证据支持。

**第一层：Recall，尽量不漏。**

- **Relevance Score**：和当前问题有多相关
- **Source Reliability Score**：来源是否可靠
- **Recency Score**：数据是否最新
- **Consistency Score**：是否和其他来源一致
- **Traceability Score**：是否可以追溯到原始位置
- **Verification Score**：是否经过结构化数据或确定性计算验证

**Evidence Score = relevance + reliability + consistency + traceability + verification**

```
Pitch Deck claim              0.63
Founder interview             0.58
CRM raw data                  0.91
Bank statement                0.96
Audited financial statement   0.98
```

```
User asks:
"What is the company's ARR?"

        ↓

        ↓
Evidence candidates

        ↓
Continuous scoring + reranking

        ↓
Can we verify the number?

     Yes              No
      ↓                ↓
Calculate          Refuse / qualify
      ↓
Return number
+ provenance
+ confidence
```

所以整个产品底层可以总结成四个核心模块：

**Recall → Rank → Verify → Answer/Abstain**

你们甚至可以把最核心的技术原则总结成：

**Retrieve broadly, rank continuously, verify deterministically, and abstain when evidence is insufficient.**

这比普通 RAG 更贴合你们的 Due Diligence 场景，因为你们不是单纯在“找最相关内容”，而是在**不断判断哪条证据更值得相信**。

## 4. Open Questions 页

这个很重要，因为你们避免给结论。

系统自动把 gap 变成问题，而不是 judgment。

比如：

- ARR reported in deck differs from revenue-derived ARR. What definition was used?
- Customer count in CRM differs from company materials. Which segments are included?
- FDA approval claim has no linked primary source. Please provide supporting documentation.

形式建议：

- **question list + linked evidence**
- 甚至可以做成 downloadable diligence questions

# 视觉语言上要怎么做

## 不应该强调的

- 风险总分
- 红黄绿投资建议
- AI recommendation
- “good / bad company”

# 颜色和状态建议

不要太 judgmental。

用这种状态词更合适：

- **Source found**
- **Multiple sources**
- **Reproduced**
- **Mismatch**
- **Missing raw data**
- **Insufficient evidence**

视觉上可以用：

- 中性色为主
- 差异项用强调色
- 缺失项用浅警示色
- 不要大面积“危险红”搞得像风控拒贷系统
